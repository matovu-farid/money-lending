# Rollover correction runbook

The historical correction is a per-chain operation, not a portfolio-wide rewrite. The read-only planner is `planRolloverCorrection` in `src/lib/interest/rollover-correction.ts`; the production loader, agent review, and applier are in `src/services/rollover-correction*.service.ts`. No public action or bulk apply command is exposed. The maintenance command accepts only one exact plan hash per invocation. Current rollover policy is `v4`; `v3` plans cannot be reviewed or applied after the penalty-cure statement change.

## Before any live write

1. Confirm the connected host, database, current migration level, and agent identities independently. Check that `DATABASE_URL_UNPOOLED` is the direct endpoint for the *same* database endpoint as `DATABASE_URL`; a matching database name alone is not enough. The snapshot and apply commands reject a different endpoint, including an unrelated Neon branch.
2. Before changing the schema, take a recoverable pre-migration backup with `scripts/pre-agent-migration-backup.ts` and verify it in an isolated database. The correction snapshot script requires the post-migration agent-review tables and cannot be used to create a pre-migration backup. On 2026-10-12 the local configured direct URL resolved to a different database branch (4 loans versus 67 on the application's pooled endpoint); the matching direct endpoint was independently checked read-only and supplied only for the backup operation. Do not use the mismatched configured URL for any correction snapshot or apply command.
3. Deploy and verify the correction-run and agent-review migrations on the intended database. Do not run an unrestricted migration command without checking every pending migration first.
4. Take a fresh post-migration backup for the loan correction. Its manifest must say `correctionAuditTablesInDump: true` and `historicalRateAuditTablesInDump: true`; both now require the agent-review table and `TABLE DATA` entries in the restore catalog. Run `scripts/rollover-correction-restore-rehearsal.ts` with the exact nonzero plan hash and input fingerprint against a local `DATABASE_URL_TEST`; it reviews, applies, and reconciles that chain on an isolated restore and writes an owner-only proof at `<dump>.rollover-restore.json`. The apply service verifies the full dump, checksum, catalog, and exact-chain proof. Preserve both backups and manifests outside the application host under the organization's sensitive-data retention policy.
5. Run `scripts/rollover-correction.ts` with explicit `--expect-host`, `--expect-database`, and a new `--out` path under a restricted temporary directory. This command is read-only and rejects `--apply`. Compute the report's SHA-256 checksum after review; the maintenance command requires that exact checksum.
6. Reconcile the report's live/deleted link count against the database inventory. Review the target chain's dates, fresh cash, source documents, original and proposed carry, settlement reclassifications, status, exceptions, input fingerprint, and plan hash. The default report contains pseudonymous IDs and financial amounts, so treat it as sensitive.
7. A blocked plan is audit-only. A review plan requires independent verification of every payment/waiver allocation and any paid/settled status. A ready plan also requires an exact agent review. The current verifier fails closed on chains with rate changes or penalty-waiver history until those source histories have a separate independent verifier. A failed or stale agent review cannot authorize posting.

## Apply one reviewed chain

Use `scripts/rollover-correction-apply.ts` first with `--mode=review --reviewer-agent-id=agent:<name> --review-run-id=<run>`, then separately with `--mode=apply --executor-agent-id=agent:<different-name>`. Both require explicit `--expect-host`, `--expect-database`, `--report`, `--report-sha256`, `--snapshot-manifest`, `--expected-dump-sha256`, `--plan-hash`, and `--input-fingerprint`. The report is provenance evidence; the service reloads the current source and independently recalculates dated carry and settlement allocations. The apply service requires the latest passing, unconsumed review for that chain, verifies the full backup and isolated restore proof, and checks the same evidence again under lock. Reviewer and executor agent IDs must differ. No human UI approval or administrator actor ID is used for new correction runs.

The stored review binds the plan hash, policy version, source fingerprint, and independently checked evidence. The applier briefly takes database table locks on loans, payments, waivers, rate changes, journal entries, categories, and rate audit history before reloading the source. This includes counterpart journal legs with no loan ID and prevents new source rows from appearing mid-apply; ordinary reads remain available, but writes to those tables wait. If a lock cannot be acquired within 10 seconds, the transaction aborts without applying anything and the operator must replan before retrying. It also locks chain loan and journal rows, rejects stale or blocked plans, posts balanced non-cash corrections (including reviewed interest/principal/overpayment reclassifications), atomically consumes the review, and records a correction-run ID. It does not alter cash receipts, payment dates, waivers, issuance fees, or loan statuses. A repeated application of the same run hash is a no-op.

Start with the first reviewed chain and verify its receipt/statement and ledger before another chain. Re-run the full read-only inventory after each apply. A corrected chain should propose zero principal and settlement-allocation deltas. Do not promote a blocked chain into a write path by changing its classification in a report.

The original journal rows remain intact; corrections are additional entries tied to a run ID. If a correction must be undone, stop further applications, preserve the current database state, and restore the pre-run snapshot to a separate database for comparison. A controlled rollback must check for intervening payments or edits, reverse each correction journal with an equal-and-opposite balanced journal, restore the prior loan principal/rollover fields from the run's before-summary, and write a new audit record. Never delete original or correction journals, and never restore an old whole-database backup over newer production activity without a separate recovery decision.

Late predecessor payments, missing allocations, contradictory dates, deleted successors, and receivable discrepancies require source-document or accounting resolution before replanning. The service intentionally does not guess which loan a late payment belongs to or silently reopen a paid loan.

For a blocked chain, resolve the underlying record before generating a new report:

- A payment dated on or after a successor's effective date needs documentary attribution to the predecessor or successor. A same-day payment also needs event-order evidence; database creation order is not proof of payment order. Do not change a payment date merely to bypass the guard.
- A successor dated before its predecessor's start needs the signed effective dates checked. Do not infer a replacement date from entry timestamps.
- A deleted successor with orphaned payment journals or an unreconciled receivable needs an accounting reconstruction. Do not restore or relink it just to make a chain eligible.
- A paid or collateral-settled successor with a residual corrected balance needs an explicit resolution of its settlement, overpayment, or status. Do not silently reopen it.

For a review chain, compare every proposed interest/principal/overpayment allocation with the receipt and agreed loan terms. The independent agent verifier records source digests and recalculated allocations against the exact plan. A plan that proposes no change to one payment can still change another payment in the same chain.

## Separate historical paid-rate correction preview

Rate corrections on loans that already have payments are a separate accounting repair, not a normal rate edit and not an automatic part of the rollover-chain command. Run the single-loan, read-only `scripts/historical-rate-repair-preview.ts` with explicit `--expect-host`, `--expect-database`, `--loan-id`, and an exact `--as-of` ISO instant with timezone (for example `2026-10-10T23:59:59.999+03:00` for the end of 10 October in Kampala). A date alone is rejected because it would silently omit receipts later that day. Optional `--out=/private/tmp/<unique-name>.json` writes an owner-only report without overwriting an existing file. This script has no apply mode. It shows each unchanged receipt amount/date alongside its old and proposed interest/principal/overpayment allocation, plus the source fingerprint and plan hash.

The corrected rate is the loan's final authorized rate, applied from recorded `start_date`. The preview replays today's interest-first calculation through each payment date; it never uses `created_at` as an effective date. An issuance fee collected through a separate Cash/Issuance Fees journal is included in the source reconciliation. Cash location and sub-location must match the loan record. A blocked report is not permission to edit the history by hand.

On 2026-10-10, provisional read-only previews of the three inventoried paid-rate loans classified two standalone loans as `review` (4 and 8 payments, respectively) and the third as `blocked` because it belongs to a rollover chain and has a same-time settlement ambiguity. Those early reports used midnight UTC and predated later source-validation fixes; regenerate them before agent review.

The historical apply entrypoint is `scripts/historical-rate-repair-apply.ts`. Run `--mode=review` with the owner-only exact report, `--expect-host`, `--expect-database`, `--reviewer-agent-id=agent:<name>`, and `--review-run-id=<run>`; this records independently checked evidence without posting journals. Before apply, take a fresh full-data snapshot with `scripts/rollover-correction-snapshot.ts`, then run `scripts/historical-rate-restore-rehearsal.ts --backup-manifest=/private/tmp/<name>.dump.manifest.json --backup-sha256=<exact SHA-256> --report=<exact owner-only report>` using the matching live `DATABASE_URL` and direct `DATABASE_URL_UNPOOLED` plus a separate loopback `DATABASE_URL_TEST` pointing to the local `money_lending` database. The rehearsal restores to a new `money_lending_rehearsal_historical_*` database, applies and reconciles that exact plan, and writes an owner-only `<dump>.historical-restore.json` proof; it never writes to the live database. The archive must have `TABLE` and `TABLE DATA` entries for loans, loan balances, payments, waivers, rate requests, journals, transaction categories, audit log, historical repair tables, and agent reviews. Historical apply refuses an absent, stale, or mismatched proof. Rollover and portfolio repairs have separate restore proofs and do not require an unrelated historical-rate rehearsal.

Run `--mode=apply` with the same report and database identity, `--executor-agent-id=agent:<different-name>`, `--backup-manifest`, and `--backup-sha256`. The apply path checks the latest passing exact review, backup, historical restore proof, report, and source under a serializable transaction. There is no human UI approval for new historical correction runs. If an account category or source fact changes, generate a new report and agent review before applying.

A read-only check found zero `interest_accrual` journal entries and 45 active loans. The repair-run and correction-leg counts remained zero. Do not bypass the account-category guard. Adding the missing category may enable the scheduled accrual worker for the whole active portfolio; treat that as a separate reviewed operational change. After any category addition, take a fresh backup, regenerate the preview, and obtain a new exact agent review before applying Daglas. Do not infer a review for Lydia or any blocked rollover chain.
